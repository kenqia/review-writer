# 用户使用说明

## 这版工具能帮你做什么

当前版本先解决综述项目最容易被忽略、但会直接影响可信度的问题：把用户提供
的来源文件和项目目标固定下来，并在后续工作前检查它们有没有被替换或越界引用。

这意味着你可以先得到一个可靠的项目起点，但还不会自动得到一篇综述。自动检索、
模型写作、人工判断和 DOCX/PDF 导出仍属于后续产品阶段。

## 开始前

需要：

- Python 3.11 或更新版本；
- 一个本地项目目录；
- 用户自己准备的 MAIN 论文和可选 SI 文件；
- 当前目录中安装 requirements.txt 声明的 jsonschema。

建议不要把真实论文、SI、解析结果和项目输出提交到 Git。可以把项目放在仓库
外部，或者使用仓库已约定的外部数据根目录。

## 第一步：准备文件

把来源放在项目的 inputs/papers 下。目录名只是组织方式，真正的绑定由命令
中的 --source 明确写出：

```text
my-review/
└── inputs/papers/
    ├── paper-1/main.pdf
    └── paper-1/si.pdf
```

每个来源绑定格式为：

```text
SOURCE_ID:PAPER_ID:ROLE:相对路径
```

其中 ROLE 只能是 MAIN 或 SI，相对路径相对于
my-review/inputs/papers。例如：

```text
P1_MAIN:P1:MAIN:paper-1/main.pdf
P1_SI:P1:SI:paper-1/si.pdf
```

必须为每篇论文提供且只提供一份 MAIN；SI 只能和同一篇论文的 MAIN 配对。
路径不能使用绝对路径、..、反斜杠、重复分隔符或符号链接绕过项目根目录。

## 第二步：创建项目

```bash
python3 scripts/project.py init \
  --project-root ./my-review \
  --project-id visible-light-review \
  --project-title "可见光驱动烯烃双官能化综述" \
  --goal "比较所提供论文中的反应模式、条件和机制证据" \
  --scope "只使用本地提供的 MAIN 与 SI 文件，不进行开放检索" \
  --source P1_MAIN:P1:MAIN:paper-1/main.pdf \
  --source P1_SI:P1:SI:paper-1/si.pdf
```

成功后会得到：

```text
my-review/
├── project.manifest.json
├── inputs/papers/
├── outputs/project-state/
└── exports/
```

命令会输出项目 ID、来源数量、每个来源的 SHA-256 和规范化配置哈希。它不会
复制、改写或上传你的来源文件。

如果 project.manifest.json 已存在，命令会拒绝覆盖。这是为了避免一次误操作
悄悄改变已有项目的输入；需要新项目时请使用新的项目目录或项目 ID。

## 第三步：验证项目

```bash
python3 scripts/project.py validate --manifest ./my-review/project.manifest.json
```

看到 status=VALID 且命令返回码为 0，说明当前 manifest、来源路径和文件哈希
满足 M0 约束。这个命令只读文件并重新计算哈希，不会写回 manifest。

常见错误：

| 错误码 | 对用户意味着什么 | 处理方式 |
| --- | --- | --- |
| PROJECT_MANIFEST_SCHEMA_INVALID | manifest 字段或枚举不符合规格 | 对照项目规格修正字段 |
| SEED_SOURCE_ROOT_INVALID | inputs/papers 不存在或不是目录 | 建立目录后放入来源 |
| SOURCE_PATH_REPARSE | 路径是符号链接、越界或不是普通文件 | 使用项目内的真实文件 |
| SOURCE_INPUT_INVALID | 来源文件不存在或来源路径无法通过安全检查 | 确认文件位置和相对路径 |
| SOURCE_ID_DUPLICATE | 两个来源用了同一 ID | 为每个来源分配唯一 ID |
| PAPER_MAIN_CARDINALITY | 一篇论文没有恰好一份 MAIN | 修正 --source 绑定 |
| SOURCE_CONTENT_DRIFT | 使用中的文件字节已不同 | 确认是否有意替换；有意替换时建立新版本项目 |
| PROJECT_MANIFEST_EXISTS | 初始化会覆盖已有项目 | 改用新目录，不强行覆盖 |

## 修改输入后的做法

不要直接替换一个已经参与下游结果的文件然后继续工作。先重新运行
validate，记录新的来源哈希；如果项目已经有不可变快照，应把这次变化视为
新输入，并重新开始受影响的阶段。M0 不会自动替你伪造迁移或批准新科学结论。

## 查看已有快照状态

当后续工作流已经产生不可变快照时，可以运行：

```bash
python3 scripts/project.py status \
  --manifest ./my-review/project.manifest.json \
  --snapshot ./my-review/outputs/project-state/run-manifest.json
```

CONFIG_CURRENT 表示当前规范化配置与该快照一致；CONFIG_CHANGED 表示配置
变化，报告会列出需要重新检查的阶段。status 要求输入是真正封闭的快照包，
不会接受只有一个哈希字段的手写替代品，也不会因为配置变化就自动标记项目 READY。

如果你还没有快照，先使用 validate；不要手工拼一个快照文件来绕过检查。

## 当前不能做什么

- 不开放检索，不联网，不调用模型，不上传论文；
- 不读取 PDF 的科学语义，不猜测分子结构，不确认作者机制；
- 不自动生成综述正文、DOCX 或 PDF；
- 不提供多用户协作、数据库、部署或后台无人值守运行；
- 不把 AI 候选、文件哈希或历史报告当作真实研究者确认。

这些限制是为了让“通过验证”只表示输入和证据边界清楚，不被误读为“科学结论
已经正确”。

## 出现问题时

先保留命令输出和错误码，不要删除项目目录或覆盖来源。通常可按以下顺序处理：

1. 检查 manifest 中的项目 ID、目标、范围和来源绑定；
2. 检查每个相对路径对应的普通文件是否仍在项目根目录内；
3. 重新运行 validate；
4. 如果仍失败，把错误码、命令和脱敏后的目录结构交给维护者。

不要提供 API key、cookie、session 或其他认证内容。
