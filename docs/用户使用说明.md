# 用户使用说明

这份说明只回答用户最关心的四件事：要准备什么、运行后得到什么、失败时怎么
处理、哪些结果还不能当成科学结论。

## 1. 这版工具解决什么问题

你已经选好一个综述主题和一组论文后，最容易出错的不是“少写了一段文字”，而是：

- MAIN、SI、解析结果和 Chemical ZIP 可能属于不同论文；
- 文件被替换后，旧证据仍被误当成最新证据；
- 20 篇和 40 篇的计数被旧三篇或 309 的历史逻辑污染；
- AI 候选看起来完整，却没有研究者确认。

当前版本先把这些输入和证据边界固定下来。它让后续结果更可检查，但不会自动替你
做科学判断。

## 2. 你需要准备什么

### 2.1 论文材料

准备 `20–40` 篇论文，每篇都要有：

1. 一份 MAIN PDF；
2. 一份与该 MAIN 明确配对的 SI PDF；
3. 论文的 DOI、标题、唯一 `study_id` 和唯一 `source_id`；
4. `tier=core` 或 `tier=background`。

不要把同一个 SI 文件路径或同一份 PDF 字节复用给两篇论文。系统会拒绝跨 study
复用，即使文件内容看起来一样。

### 2.2 五个 Review Questions

请求中的 `brief.review_questions` 应包含五个问题。当前 Approved Spec 的权威问题是：

1. 主要键组合、反应模式及活化策略是什么？
2. 条件如何影响表现，哪些结果不可直接比较？
3. 底物范围、耐受性、选择性和局限是什么？
4. 机制证据处于什么层级，作者解释之间有哪些冲突？
5. 通用性、选择性、放大、资源效率和机制确定性还存在哪些缺口？

### 2.3 文件 hash

对每个 MAIN/SI 计算小写 64 位 SHA-256：

```bash
sha256sum /data/papers/study-001-main.pdf
sha256sum /data/papers/study-001-si.pdf
```

hash 不代表论文结论正确，只表示系统以后能发现文件字节是否改变。

## 3. 创建项目

请求文件必须符合
`schemas/project/corpus_manifest.v1.schema.json`。关键字段如下：

```json
{
  "schema_version": "corpus-manifest.v1",
  "project_id": "visible-light-review",
  "brief": {"topic": "可见光驱动烯烃双官能化", "review_questions": ["..."]},
  "sources": [
    {
      "study_id": "study-001",
      "source_id": "source-001",
      "doi": "10.example/one",
      "title": "论文标题",
      "tier": "core",
      "document_role": "MAIN",
      "pdf_input_path": "/data/papers/study-001-main.pdf",
      "expected_pdf_sha256": "...",
      "si_pdf_input_path": "/data/papers/study-001-si.pdf",
      "expected_si_pdf_sha256": "..."
    }
  ]
}
```

实际文件必须有 20–40 条 `sources`；上面的示例只是字段示意，不能直接作为完整
运行请求。

执行：

```bash
python scripts/run_vertical_review.py bootstrap-corpus \
  --review-root /data/review-projects \
  --request /data/requests/visible-light-review.json
```

用户得到的变化：

- 项目只从本次请求创建，不复制旧项目的下游状态；
- MAIN 会放入 `00_sources/papers/`，SI 会放入
  `00_sources/supplements/imported/`；
- `00_sources/acquisition_final_receipt.json` 记录每个 study 的输入 hash；
- `00_sources/source_coverage.json` 记录 MAIN/SI 可用性。

如果目标目录或外部 canonical anchor 已存在，命令会拒绝覆盖已有内容。

## 4. 绑定 Generic Parse

对项目中 `00_sources/` 下的全部 PDF 完成 Generic/MinerU 解析。变量语料必须得到
`2N` 个 completed rows：每个 study 一条 MAIN、一条 SI。输出目录至少需要：

```text
generic-output/
├── manifest.json
├── markdown/<slug>.md
├── extracted/<slug>/full.md
├── extracted/<slug>/layout.json
├── extracted/<slug>/*_content_list.json
├── extracted/<slug>/*_content_list_v2.json
└── raw_zips/<slug>.zip
```

绑定：

```bash
python scripts/run_vertical_review.py bind-generic-parse \
  --project /data/review-projects/visible-light-review \
  --mineru-output /data/mineru/visible-light-review
```

用户可看到的变化：

- `01_evidence/mineru/manifest.json` 和 `01_evidence/parses/manifest.json`；
- `01_evidence/text_layers/text_layers.manifest.json`；
- 每个 study 的 `01_evidence/source_truth/<study_id>/bundle.json`；
- 每个 study 的 `parse_quality.json`。

MAIN 的 text-layer identity 使用原 `source_id`，SI 使用 `<source_id>__SI`，这样两层
不会因文件名相同而混在一起。变量语料只接受完整相对路径绑定；不能靠 basename 猜
归属。

## 5. 准备输入 provenance manifest

这是第二个 JSON，不是 bootstrap 请求。它声明每个 study 的页数、SI 原始文件和
Chemical ZIP：

```json
{
  "schema_version": "input-provenance-manifest.v1",
  "project_id": "visible-light-review",
  "studies": [
    {
      "study_id": "study-001",
      "source_id": "source-001",
      "main_pdf": {"sha256": "<MAIN hash>", "page_count": 12},
      "si": {
        "input_path": "/data/papers/study-001-si.pdf",
        "sha256": "<SI hash>",
        "page_count": 8
      },
      "chemical_zip": {
        "input_path": "/data/chemical/study-001.zip",
        "sha256": "<ZIP hash>",
        "page_count": 8
      }
    }
  ]
}
```

它也必须包含完整的 20–40 篇 study，不能漏掉或重复 study/source。

先做只读检查：

```bash
python scripts/run_vertical_review.py preflight-corpus-inputs \
  --project /data/review-projects/visible-light-review \
  --manifest /data/requests/visible-light-inputs.json
```

成功时会返回 `status=ready_for_import`，并披露按 `N`、`K` 计算的数量：

```text
main_pdf=N/N
si=N/N
generic_main=N/N
generic_si=N/N
chemical_main=N/N
chemical_core_si=K/K
```

如果缺 MAIN/SI、hash 不匹配、解析过期、Generic 错绑、Chemical ZIP 错绑或路径
跨 study 复用，检查失败。失败时不应手工改项目 JSON 来“补绿”。

## 6. 发布输入 provenance

只在 preflight 成功后执行：

```bash
python scripts/run_vertical_review.py import-corpus-inputs \
  --project /data/review-projects/visible-light-review \
  --manifest /data/requests/visible-light-inputs.json \
  --actor-type human_researcher \
  --actor-label "肯恰大人"
```

这一步会发布：

- `00_sources/input_provenance_manifest.json`；
- `00_sources/si_resource_registry.json`；
- 更新后的 `00_sources/source_coverage.json`；
- 每个 study 的 SI 副本、Chemical Paper 状态和 dual-source/parse reconciliation
  下游绑定。

它不会：

- 替你确认分子结构；
- 把 AI 候选变成 `CONFIRMED`；
- 证明正文、综合、DOCX/PDF 已完成；
- 代替真实研究者对具体物质声明的决定。

## 7. 三种科学状态

| 状态 | 你应该如何理解 | 能否直接写成精确事实 |
| --- | --- | --- |
| `CONFIRMED` | 真实合格研究者已基于唯一 MAIN/SI 证据明确确认 | 可以，但仍需满足完整 claim trace |
| `AI_PROVISIONAL` | 有定位、来源和置信度的未确认候选 | 不能，必须显式标未确认 |
| `BLOCKED` | 无法唯一确定，已记录原因 | 不能，应改写为限制或排除 |

模拟研究者 actor 仍是模拟 actor，不得写成“用户已接受”。

## 8. 常见错误和恢复方式

| 错误类别 | 对用户意味着什么 | 正确恢复方式 |
| --- | --- | --- |
| `BOOTSTRAP_REQUEST_INVALID` | 请求字段缺失、SI 缺失或不符合 20–40 合同 | 修正请求后使用新的 project ID 重试 |
| `SOURCE_PDF_HASH_MISMATCH` / `SOURCE_SI_HASH_MISMATCH` | 输入文件和声明的 hash 不一致 | 重新计算 hash，确认文件版本 |
| `DUPLICATE_SOURCE_PDF` | 两个文档复用了同一 PDF 字节 | 找到每个 study 的正确文件，不能复制声明 |
| `GENERIC_PARSE_INCOMPLETE` | Generic 没有完成全部 `2N` 文档 | 补齐解析后重新绑定；不要手改 manifest |
| `GENERIC_*BINDING*` | 解析结果指向错误 study、角色或 hash | 重新生成与当前项目一致的解析输出 |
| `SI_*` / `INPUT_BINDING_AMBIGUOUS` | SI 缺失、过期或跨 study 复用 | 检查路径、hash 和项目对应关系 |
| `CHEMICAL_*` | Chemical ZIP 缺失、损坏或身份不匹配 | 重新导出正确 ZIP；保留失败报告 |

同一个候选修复连续失败时，应停车并保留错误证据，不要扩大范围重写系统。

## 9. 当前限制与下一步

当前没有真实 20–40 篇主题语料的完整 science run 证据，因此不能宣称：金标准通过、
研究者授权发布、DOCX/PDF 已生成或 12 小时无人值守成功。下一步应先由用户提供
完整且合法的 MAIN/SI/Generic/Chemical 输入，再单独进行 Dashboard、Evidence、
Synthesis、manuscript 和导出验收。

不要提供 API key、cookie、session、auth 文件或其他认证内容。
