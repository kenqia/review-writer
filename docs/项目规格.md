# review-writer 当前项目规格

版本：`variable-N / 20–40` 输入与证据基础线

依据：当前 v0.1 的用户输入合同、运行时实现和可复现的本地验证结果。

本规格描述用户现在能依赖的边界，不把历史 M0、旧三篇案例、旧 309 分母或旧
Dashboard 运行记录当作当前产品承诺。

当前用户启动入口是 `scripts/run_vertical_review.py` 的四步 variable-N CLI：
`bootstrap-corpus`、`bind-generic-parse`、`preflight-corpus-inputs`、
`import-corpus-inputs`。本分支只保留这条 MVP 用户流程需要的内容；开发轨迹、旧技能
和历史资产保留在 `core-development` 分支，不是当前主入口。

## 1. 用户目标

用户提供一个主题、五个 Review Questions、20–40 篇论文的 MAIN/SI、核心论文
清单和规定的化学解析后，系统先可靠回答：

1. 每篇论文的 MAIN、SI、Generic Parse 和 Chemical ZIP 是否确实属于同一个 study？
2. 文件和解析结果是否仍然是当前版本？
3. 哪些证据可以进入后续 Paper Evidence 和综合？
4. 哪些分子或材料结论仍是 `AI_PROVISIONAL` 或 `BLOCKED`？
5. 输入缺失时用户应该修复哪一个文件，而不是重做整个项目？

## 2. 用户可见能力

| 能力 | 用户得到的改变 | 入口 | 当前限制 |
| --- | --- | --- | --- |
| variable-N bootstrap | 能创建 20–40 篇的新鲜项目，不再被三篇固定入口限制 | `bootstrap-corpus` | 需要用户提供完整 MAIN/SI 元数据和 hash |
| MAIN/SI 绑定 | 每篇论文都有成对且 hash-bound 的 PDF 记录 | bootstrap receipt | 不判断论文的化学正确性 |
| Generic Parse 绑定 | 每个 study 有独立 MAIN/SI text-layer 和 Source Truth | `bind-generic-parse` | 必须提供完整 `2N` 解析输出 |
| Parse Quality | 能发现正文、图表、公式、参考文献或 SI 完整性问题 | bind 后自动生成 | 自动检查不等于人工科学批准 |
| 输入 preflight | 在写项目状态前发现缺失、错 hash、过期和跨 study 复用 | `preflight-corpus-inputs` | 需要另一个输入 manifest |
| provenance 发布 | 将 current 输入绑定写入 artifact、SI registry 和 coverage | `import-corpus-inputs` | 只记录输入和 Chemical import，不确认分子 |
| 三态科学状态 | 用户能区分已确认、未确认候选和阻断项 | 下游 projection | 不是四步输入命令的自动结果；`CONFIRMED` 必须由真实合格研究者决定 |

### 用户逐步得到什么

| 步骤 | 用户执行 | 用户得到的变化 | 失败后的最小动作 |
| --- | --- | --- | --- |
| 1 | `bootstrap-corpus` | 新鲜项目、MAIN/SI receipt 和 source coverage | 修正请求或 hash，换新 `project_id` |
| 2 | `bind-generic-parse` | 每个 study 的 MAIN/SI Generic identity、Source Truth、Parse Quality | 修复外部 `2N` 输出后重试，不覆盖已有 `01_evidence/` |
| 3 | `preflight-corpus-inputs` | 只读的实际 `N/K` 计数和阻断原因 | 修复对应输入/manifest，再重复 `preflight-corpus-inputs` |
| 4 | `import-corpus-inputs` | current 输入 provenance、SI registry、coverage 和 Chemical import 绑定 | 保留错误证据，重新运行 `preflight-corpus-inputs`；禁止手改 JSON |

这四步只建立可检查的输入基础线。它们不自动生成真实综述，不代表研究者确认，也不
代表 DOCX/PDF 已生成。

## 3. 权威输入合同

设论文数为 `N`，核心论文数为 `K`：

```text
20 <= N <= 40
MAIN_PDF_READY=N/N
SI_PDF_READY=N/N
GENERIC_MAIN_READY=N/N
GENERIC_SI_READY=N/N
CHEMICAL_MAIN_READY=N/N
CHEMICAL_CORE_SI_READY=K/K
SOURCE_TRUTH_CURRENT=true
```

每条绑定必须唯一、current、hash-bound。缺失、损坏、错绑、跨论文复用、hash
不一致和 stale 都是阻断条件，不能改成 warning。

用户把请求 JSON 和项目输出分别放在仓库内的 `inputs/` 与 `projects/`；原始 PDF、
Generic 输出和 Chemical ZIP 可以放在仓库之外。`projects/<project_id>/` 是命令创建
的新项目目录，不能预先放入历史下游状态。bootstrap 请求装入 MAIN/SI；Generic 输出
必须由用户另行准备；Chemical ZIP 在 provenance preflight/import 时对每个 study
必须存在并能按 hash、页数和来源绑定。

### MAIN 与 SI

- bootstrap 请求的每条 source 必须同时有 `pdf_input_path/expected_pdf_sha256`
  和 `si_pdf_input_path/expected_si_pdf_sha256`；
- MAIN 项目路径为 `00_sources/papers/<source_id>.pdf`；
- SI 项目路径为 `00_sources/supplements/imported/<source_id>.pdf`；
- receipt 的 SI descriptor 与实际复制字节一致；
- SI source identity 使用 `<source_id>__SI`，与 MAIN identity 分离。

### Generic Parse

变量语料的外部 manifest 必须完成 `2N` 个文档。每个 row 至少要能通过相对路径和
`source_pdf_sha256` 对回项目 PDF；若提供 `study_id/document_role/source_id`，
它们也必须与当前绑定一致。变量语料不能用同名 basename 代替完整路径。当前 CLI
只绑定已有 Generic 输出，不负责替用户运行解析器或上传原始 PDF。

### Chemical Parse

Chemical ZIP 是独立输入 lane。`CHEMICAL_MAIN_READY` 和核心 `CHEMICAL_CORE_SI_READY`
是输入绑定数量，不代表所有分子都已确认。raw extraction、候选 JSON 和导入摘要
不能直接进入科学正文；`import-corpus-inputs` 的 actor 字段也只是记录 provenance
发布者，不创造真实研究者决定。

## 4. 科学状态和证据链

唯一允许的分子/材料状态是：

- `CONFIRMED`：原始 MAIN/SI 唯一支持，且真实合格研究者明确确认；
- `AI_PROVISIONAL`：有 locator、provenance、confidence，但仍未确认；
- `BLOCKED`：不能唯一确定，`value=null`，并记录 gap reason。

禁止猜测 SMILES、使用 `R-group`/`[*]` 充当最终结构、把语法有效当成科学正确，
或把模拟研究者写成真实用户。

物质性 claim 必须能沿下面的链路往返：

```text
Source Manifest/PDF hash
  -> Paper Evidence
  -> Claim/Decision
  -> Review-Question Matrix
  -> 权威 manuscript
  -> Gap Registry/Artifact Manifest
  -> DOCX/PDF
```

任一边缺失，claim 必须降级为限制、排除或 `BLOCKED`。

## 5. 当前不包含

为了让用户入口少而可靠，当前主线不新增：

- 开放式论文 discovery、第二主题或第二套大语料；
- 新 Provider、RAG、SaaS、部署、多用户、数据库和通用框架重构；
- 自动科学确认、自动猜结构或把 candidate 直接注册为结论；
- 以 309、固定三篇、旧 Case ID 或单个项目路径硬编码公共产品；
- 将历史 Phase 8、Bailian、QoderWork 迁移、旧 release 修复波次作为用户入口。

开发回归代码、fixture、测试和历史轨迹保留在 `core-development`，不进入用户主路径；
用户不需要接触它们，也不应把它们当成产品输出。

## 6. 成功和失败边界

当前代码级输入完成可以表示为：

```text
SCALED_CODE_READY=OK       # 仅在新鲜代码检查满足后
SCALED_INPUT_READY=OK      # 仅在真实 N/K 输入绑定满足后
SCALED_RUNTIME_READY=OK    # 需要真实 Dashboard/Playwright 证据
SCALED_REVIEW_READY=OK     # 需要 Evidence/Synthesis/benchmark/DOCX/PDF audit
```

本工作树只有代码和 synthetic 回归证据，不能据此宣称后面三个状态已经为 OK。
真实运行仍可能因输入、解析、科学决定、综合、benchmark 或导出失败。

失败处理必须保持 fail-closed：只读 `preflight-corpus-inputs` 失败时不发布正式状态；
`import-corpus-inputs` 失败时
不以 warning 代替缺失输入，也不允许用户手工修改 JSON 伪造 `CURRENT`。用户应保留错误
代码和输入版本，修复对应外部文件后重新运行 `preflight-corpus-inputs`；目标已存在或 Generic 目标已有
`01_evidence/` 时，禁止覆盖，必要时从新的 `project_id` 创建 fresh project。

允许对当前代码重新打开的 P0/P1 只包括：variable-N 阻断、强制输入无法 current
绑定、Source Truth/科学状态/workflow gate 矛盾、主 Dashboard 路径不可用、Evidence
无法闭环、benchmark/DOCX/PDF audit 无法完成、fresh project 被旧状态污染，或敏感
信息泄露。其他改进进入停车场，不继续横向扩张。

## 7. 对用户的下一步

用户下一步不是删除历史文件，而是准备一份真实、合法、完整的 20–40 篇输入包，
先通过 `preflight-corpus-inputs`，再单独验收 Dashboard、Evidence、五个综合矩阵、
manuscript 和导出。任何“通过”都只说明对应层级通过，不能被扩大解释为论文已发表
或领域专家背书；历史开发路径也不能改变这个边界。
